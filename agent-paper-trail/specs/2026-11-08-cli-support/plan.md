# CLI and native path opening implementation plan

Status: Unit 1 accepted; later units retain their decision gates. Implement native path opening first, then the bundled launcher, then setup and usage documentation. The [spec](spec.md) owns the proposed behaviour, [tasks](tasks.md) owns readiness, and [validation](validation.md) owns acceptance.

Each coding unit requires approval. Finish each unit with tighten, probe, appropriate automated checks and a signed running app for manual acceptance before starting the next. Commit, push, merge and release require separate approval.

Unit 1 uses the accepted [window and request policy](spec.md#window-and-request-ownership), native access and focus/error rules. External opens clear their target query as an exception to A41 and take precedence over A27's target restoration. Decide CLI defaults, path semantics, transport, preflight outcomes and Terminal signing before Unit 2. The checks below define required validation; task evidence records execution.

## Integration boundaries

`PanePeekApp` declares one browser `WindowGroup`. Its app-level commands supply the scene opener before any browser exists; native file-open launch can suppress automatic initial-window creation. `BrowserLifecycle` owns registered windows and pending scene requests; `WindowRestoration` starts each window once. Reuse `BrowserState.navigate` for rename and dirty-document guards, and `DirectoryPane` for applying listings and selection while rejecting stale results. `openContainingFolder` requires an item already in the listing, so external paths need a new entry into the existing guarded flow.

`FolderAccess.read(..., exact: true)` restricts chooser replacement but can follow a moved bookmark. `readAccess(for:)` checks the saved target path before reuse. Build on these mechanisms to keep an incoming path at its intended location without changing bookmark relocation for restoration or history.

Native and scripted bundles share `xcode/Info.plist` values through `scripts/bundle-metadata.mjs`. Validate nested document/URL declarations there rather than duplicating the metadata.

## Unit 1: Native incoming paths

**Result:** `open -a <review-app> <folder-or-file>` reaches the requested destination on cold launch, while running and after all browser windows close. This unit excludes the launcher, custom CLI URL protocol and setup.

1. **Receive and assign the request.** `BrowserLifecycle` handles the native [URL-open callback](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/application%28_%3Aopen%3A%29); the SwiftUI app supplies scene creation and identity through app-level commands. Reuse the most recently active browser still registered. During cold launch, reserve the system's initial scene identity; at launch completion, open that identity if its destination is still pending. Keep the opener available before any browser exists and coalesce creation with any automatic initial presentation. When already running without windows, create one scene and coalesce pending creation requests. Bind both the destination and restoration choice to its identity so an explicit New Window stays fresh. Reject multiple URLs before navigation. Keep only the newest pending destination for the captured window/browser, cancel it on close or quit, and defer permission UI until any attached sheet closes.
2. **Prepare startup.** For the identified scene, restore layout and choose its active browser before directory reads. Restore the other browser and retain the target's remembered path/bookmark without loading it. Skip the obsolete target read, history and error; preserve the saved record until success. Supersede an already-running target read instead of waiting indefinitely, rejecting its late results while the other browser restores independently. A failed first open shows its error and the remembered path/access guidance without an old listing or Home fallback. Ordinary A26/A27 behaviour stays intact.
3. **Acquire access, then resolve edits.** Try a live folder grant, saved bookmark, applicable access from an incoming directory URL, then a covering chooser. Retain native URLs and scopes under the reviewed native-access lifetime/mode policy; a file grant does not cover its parent. Check the intended location against moved bookmarks and authorised link resolution, then reuse the existing rename and dirty-document guards, listing and preview flow. A later read failure does not undo an explicit Save or Discard.
4. **Apply the destination together with its selection.** Keep browsing a folder versus selecting an item in its parent separate from item type. Resolve the actual entry using filesystem naming rules and its own identity/spelling, preserving a link actually received and avoiding arbitrary hard-link matches. Native opening accepts a target resolved by macOS before delivery; the launcher's literal-link handoff remains with Unit 2. Apply the successful directory, cleared query, required hidden visibility and selection together. Reuse query clearing that already works for a non-hidden selected item; ordinary navigation retains its query under A41. Keep one navigation flow rather than adding a second pipeline or generic request framework.
5. **Declare supported native opens.** Add shared document declarations without claiming default ownership of users' file types. Verify native and scripted bundles, including review identities.

Likely changes: `PanePeekApp`, `BrowserWindow`, `BrowserLifecycle`, `WindowRestoration`, `BrowserState`, `FolderAccess`, shared bundle metadata and their existing tests. Extract code only where a concrete ownership boundary makes it smaller. Keep one event handler: do not also process the same event through `.onOpenURL`. Apple's [scene selection](https://developer.apple.com/documentation/swiftui/scene/handlesexternalevents%28matching%3A%29) and [open-scene preferences](https://developer.apple.com/documentation/swiftui/view/handlesexternalevents%28preferring%3Aallowing%3A%29) inform routing; actual delivery, scopes and startup order need signed runtime checks.

**Automated validation:** use red/green behaviour tests in the existing access, navigation and restoration fixtures. The [validation matrix](validation.md) owns the full scope. Include a cold open before initial scene registration, New Window during pending creation, no Dock callback, one scene for repeated requests, correct restored browser identity, no obsolete target history/error and the saved record after a failed initial open. A request must proceed while an old target read is blocked, and ignore its later completion. Test busy-sheet deferral separately from panel cancellation; cover denied access, moved bookmarks, replaced paths, dirty/rename decisions, invalidation and atomic hidden selection/query clearing. Check case variants on an insensitive volume, distinct names on a sensitive volume, Unicode, ancestor links, hard links, packages, dangling links and root. Directory reveal must use this same flow in Unit 2.

**Native validation:** run targeted checks through `node scripts/test.mjs`, with native selections serialised. Compare opening/switching against unchanged main. Build a certificate-signed sandbox review app and inspect both bundle metadata paths. Exercise actual `open -a` delivery across launch states, one-window creation, multi-URL rejection, two existing windows, both browser modes and permission/dirty outcomes. Check destination focus and captured window/browser ownership, plus the [shared accessibility checks](../../validation/checklist.md#accessibility-checks) for chooser/error UI. Fixtures verify behaviour; signed `open -a` runs verify Launch Services delivery.

## Unit 2: Bundled launcher and reveal handoff

**Prerequisites:** Unit 1 accepted; launcher packaging, signing and transport choices reviewed and verified. Until then, this unit is not ready for coding.

Compare a small native launcher with a bundled system-shell launcher for size, safe argument/path handling, runtime availability and distribution support. Verify execution from Terminal in both GitHub and Store configurations. Apple's [embedded-tool guidance](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app) does not establish that inherited helper entitlements work for a Terminal invocation.

Select an event-based browse/reveal handoff to the launcher's containing app, including when another copy is installed or running. A strictly decoded local URL is a candidate; file URLs remain the native opening route. Keep current capabilities. Bring infeasibility or a required contract change back for review before implementation.

Implement the reviewed command contract and explicit path semantics; do not simplify symlink traversal as string components. Help/version must not launch the app. Route browse and reveal through Unit 1. Bound preflight work and distinguish confirmed absence from unavailable access, using the verified distribution-specific outcomes. Bundle, sign and verify through both existing build paths.

**Validation:** use red/green parsing, path and handoff tests, then real launcher runs from another working directory and through a symlink. Cover names containing spaces or Unicode, hidden items, leading-hyphen names, broken links, running-app `--reveal`, two installed copies, exact app targeting, launch failure, denied access after handoff, packaged version/build/candidate output and the documented exit statuses. Verify actual GitHub-style and Store archive/export launchers, signatures and capabilities. Compare bundle size and opening behaviour.

Document the bundled launcher location, user-local setup, PATH configuration, existing-command collisions, removal and repair after moving the app. Use the same workflow for GitHub and Store installs, without an installer UI or app-driven shell-file changes. Explain that successful handoff does not guarantee later permission or navigation.

Update the usage/contributor guides and task/criterion evidence. Validate setup and removal in a disposable PATH directory with actual packaged apps, paths containing spaces and an unrelated existing command. Open the signed app from the installed command and check the full [validation matrix](validation.md). Store submission, release allocation and publishing are excluded.
